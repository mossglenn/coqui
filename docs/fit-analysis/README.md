# Fit Analyses

Track B artifacts. Each takes a completed piece of CoQui design as a fixed input and asks what Armature would have to do to support it.

These are **analyses, not redesigns**. When a fit analysis finds friction, the outcome is one of three:

| Outcome | Meaning |
|---|---|
| **Armature gap** | The graph genuinely cannot represent or serve something a real app needs |
| **Plugin concern** | This is CoQui's UX, workflow, or storage — it never belonged in the hub |
| **CoQui adapts** | Armature's model is defensible and CoQui's assumption was the weaker one |

The third outcome is load-bearing. Without it, every friction point becomes a schema change request and the hub accumulates one application's idiosyncrasies.

**The triage rule:** an "Armature gap" must cite either an **Armature-internal symptom** or a **user-stated requirement**. "CoQui needs it" makes it a plugin concern until proven otherwise.

Fit Analysis 01 originally reported nine Armature gaps. Three survived scrutiny. Every survivor met that bar; every withdrawal failed it. The document preserves its own errors rather than hiding them, because the correction pattern is itself a result.
